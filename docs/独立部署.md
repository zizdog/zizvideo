# 独立部署（不依赖 ZizPanel）

用户 2026-10-11 的目标：**没有面板的机器也要能装、能扫、能升级**。这份文档讲两件事：
怎么装（macOS / Linux），以及**装完必须做的"完全磁盘访问"授权**（独立部署没人替你申请）。

---

## 一、macOS（一键安装）

```bash
curl -fsSL https://mirror.zizdog.com:8888/apps/zizvideo/install-zizvideo.sh | bash
# 或者先下载再跑（能看清脚本干了什么）：
curl -fsSLO .../install-zizvideo.sh && bash install-zizvideo.sh
```

常用参数：

| 参数 | 作用 |
|---|---|
| （默认）`--system` | 系统级 LaunchDaemon：开机即起、不需要登录。写 `/Library/LaunchDaemons` 并 bootstrap 系统域，需要 sudo |
| `--user` | 用户级 LaunchAgent：只在有人登录后运行。无 sudo 时才用它 |
| `--listen host:port` | 改监听地址（写进 config 并回读确认） |
| `--upgrade` / `--uninstall` / `--purge` | 升级 / 卸载（保留数据）/ 连数据一起删（需二次确认） |
| `--dry-run` | 只打印要做的事 |

装到 `~/.local/bin/zizvideo`，数据在 `~/Library/Application Support/zizvideo`，日志在 `~/Library/Logs/`。
**与面板托管互斥**：系统域里已经有 `cn.zizpanel.zizvideo` 时脚本会拒绝独立安装（同一个 7766 端口）。

### 1.1 完全磁盘访问（独立部署的关键一步）

TCC（隐私保护）拦的是"**读**"这个动作。受保护的位置包括：外置卷、`~/Desktop`、`~/Documents`、
`~/Downloads`、照片图库、邮件等 —— 权限位看着正常，`open` 照样被拒。

- 面板托管时：**面板**持有这个授权，zizvideo 作为它的子进程继承 ⇒ 你不用管。
- **独立部署时**：授权必须给 **zizvideo 自己的二进制**，否则那些目录里的视频**不会被扫描到**。

安装器会自动做这件事：

1. 装完服务后，读你 config 里的 `media_allow_roots`；
2. 写一个**一次性 launchd 作业**，让 **launchd 直接执行** `zizvideo check-access <每个媒体根>`
   —— 为什么绕这一下：TCC 把权限归给**发起进程**，安装器是在你的终端里跑的，终端可能已经授权
   （或者根本没有），用它去读测出来的**不是守护进程的权限**，会给出假结论；
3. 读得到 → 报"✓ 守护进程读得到"；读不到 → 打印引导 + 在 Finder 里选中二进制
   + 打开「系统设置 → 隐私与安全性 → 完全磁盘访问」，然后等你授权后复验（默认最多 60 秒）。

手动授权（安装器已经把你带到这一步了）：

1. 打开 系统设置 → 隐私与安全性 → 完全磁盘访问；
2. 点 `+`，按 `⌘⇧G` 粘 `~/.local/bin/zizvideo`（或直接用安装器打开的那个 Finder 窗口把它拖进去）；
3. 打开右边的开关；
4. 不用重装 —— 跑一次「扫描媒体库」或重启服务即可。**升级不会丢这个授权**（二进制是签名的）。

> 无人值守/自动化：`ZV_ACCESS_PROBE_WAIT=0 bash install-zizvideo.sh` 只报告不等待，退出码仍为 0。
> 事后再验一次：`~/.local/bin/zizvideo check-access /你的/媒体根`（输出一行 JSON，`readable` 就是答案）。
> 想看"到底有没有全盘权限"：`zizvideo check-access --fda`（**启发式**，别当判决 —— 见下）。

**为什么 `--fda` 只能是启发式**：2026-10-11 实测，本机 `~/Library/Application Support/com.apple.TCC/`
干脆不存在，而系统级 `TCC.db` 在没有 FDA 的普通进程里也可能读得到 ⇒ 用"哨兵文件读得到"下判决会
**假阳性**（比不探测更糟：会让人以为万事大吉、跳过引导）。所以它的文案写的是"**通常说明**已授予"，
真正可信的判据永远是：**去读你实际关心的那个媒体根**。

## 二、Linux（systemd）

zizvideo 是纯 Go + 内嵌前端 + SQLite，交叉编译 `CGO_ENABLED=0` 的静态二进制在 Linux 上直接可跑
（`make check` 里就有 linux/amd64 + linux/arm64 的交叉编译门禁）。Linux 侧用 `install-zizvideo-linux.sh`：

```bash
sudo bash install-zizvideo-linux.sh --listen 0.0.0.0:7766
```

它做六件事：按架构从**平台专属清单** `linux.json` 挑包 → 下载并**逐字节校验 sha256**（不符就拒）
→ 放二进制到 `/opt/zizvideo/zizvideo` → 建专用系统用户 `zizvideo` 并写 `/etc/zizvideo/config.json`
（已存在则不动）→ 装 `zizvideo.service`（systemd：开机自启、`Restart=always`、
`NoNewPrivileges/ProtectSystem=full/ProtectHome=read-only` 只放开数据目录）→ 起服务并用 `/readyz` 验收
（**验收不过就是失败**：首次安装如实报错；升级则回滚到旧二进制，绝不谎报"安装完成"）。

`--upgrade` 只换二进制；`--uninstall` 停服务（数据保留）；`--purge --yes` 连数据目录一起删并回读确认；
`--dry-run` 只走流程不落盘。Linux 没有 TCC，**不需要**完全磁盘访问那一步；外置盘只需要挂载点对服务用户可读。

**为什么 Linux 走单独的 `linux.json` 而不是 `manifest.json`**：后者是**面板的契约**（只认 darwin、
按 `arch` 选包），同一份里塞 darwin/arm64 与 linux/arm64 会让面板给 macOS 装到 Linux 二进制。
`make release` 现在同时产出 `linux/amd64` + `linux/arm64`（`CGO_ENABLED=0` 静态、不签名），
`make-app-index.py` 把它们写进 `linux.json`（有 linux 产物才写），`make publish` 会把
`linux.json` 与 `install-zizvideo-linux.sh` 传到 app 级稳定路径并复验线上可达。

## 三、升级与回滚

- 升级：重跑安装器（或 `--upgrade`）。它会保留 config、数据、以及 TCC 授权。
- 失败的升级会**回滚**：二进制与 plist 恢复成改动前，并把恢复出来的服务重新 bootstrap
  （老实现的失败升级会把用户丢在"服务停着"，脚本里现在有一条门禁盯着这个）。
- 回滚不干净时脚本会**如实说**（不会打印"没有留下半截"）。

## 四、安装器自身怎么被验证

`tools/test-installer.sh`（`make check` 的一部分，**全程沙箱**：假 launchctl / 假 sudo / 假 open / /tmp 路径）
覆盖：`--purge` 删除前守门、config 写入回读、回滚重新 bootstrap、证书指纹硬编码、交叉编译、
完全磁盘访问的四种路径（读得到 / 读不到要引导 / `--no-fda-wait` 不等待 / 探测 plist 不残留），
并断言**一次都没碰真 sudo**。

## 五、飞牛（fnOS）应用

zizvideo 在飞牛上是**独立端口服务**型的 `.fpk` 应用（对应官方文档里的 B 类：应用自带 HTTP 服务、
不需要复用 NAS 登录态）。包源在仓库 `fnos/zizvideo/`：

```
fnos/zizvideo/
├── manifest                  # key=value（**不是 JSON**）：appname/version/platform=x86/service_port=7799…
├── ICON.PNG / ICON_256.PNG   # 64×64 与 256×256（官方硬要求）
├── config/privilege          # run-as=package（最小权限，**不用 root**）
├── config/resource           # data-share: zizvideo/media（应用自己的共享目录）
├── app/ui/config             # 桌面入口 zizvideo.main + 管理员入口（readonly）
├── app/bin/zizvideo          # 打包时放进去的 Linux 静态二进制（x86 用 amd64，arm 用 arm64）
└── cmd/main                  # 生命周期：start / stop / status（没跑必须返回 3，未知参数 1）
```

打包与安装：

```bash
make release            # 会同时出 darwin 与 linux/amd64 + linux/arm64 产物
make fpk                # = tools/make-fnos-pkg.sh：准备好待打包目录，有 fnpack 就出 .fpk
make fpk FPK_ARCH=arm64 # 给 arm 设备打
# 产物：dist/fnos/zizvideo-<版本>-x86.fpk（需要官方打包器 fnpack）
# 真机安装：appcenter-cli install-fpk dist/fnos/zizvideo-*.fpk
```

**没有 `fnpack` 时脚本会如实报错**，不会伪造一个"看起来像 .fpk"的压缩包（假包会让用户装不上
还以为是我们的问题）；`--stage-only`（或 `make fpk STAGE_ONLY=1`）只准备目录。

数据与权限：数据放在应用私有目录（`TRIM_PKGVAR`，卸载默认保留）；视频放进应用的共享目录
`zizvideo/media`（`config/resource` 里声明的 `data-share`，系统会给应用运行用户授权），
或在安装向导里填一个**应用用户读得到**的绝对路径。Linux/飞牛没有 macOS 的 TCC，所以
**不需要**"完全磁盘访问"那一步。

**已知未验证**：本仓库的开发机是 macOS，没有 `fnpack`、也没有飞牛设备 ⇒ 目前能证明的是
"包结构/字段/生命周期退出码/最小权限/图标尺寸"都符合官方文档，以及待打包目录能正确生成；
**`fnpack build` 与真机 `appcenter-cli install-fpk` 尚未跑过**（这两步必须在有 fnpack 的机器
或飞牛设备上做）。`make check` 里的独立部署门禁会把上面这些结构判据逐条验一遍。
