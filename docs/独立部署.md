# 独立部署（不依赖 ZizPanel）

用户 2026-10-11 的目标：**没有面板的机器也要能装、能扫、能升级**。这份文档讲两件事：
怎么装（macOS / Linux），以及**装完必须做的"完全磁盘访问"授权**（独立部署没人替你申请）。

---

## 一、macOS（一键安装）

```bash
curl -fsSL https://mirror.zizdog.com:8888/apps/zizvideo/install-zizvideo.sh | bash
# 或者先下载再跑（能看清脚本干了什么）：
curl -fsSLO .../install-zizvideo.sh && bash install-zizvideo.sh
```

常用参数：

| 参数 | 作用 |
|---|---|
| （默认）`--system` | 系统级 LaunchDaemon：开机即起、不需要登录。写 `/Library/LaunchDaemons` 并 bootstrap 系统域，需要 sudo |
| `--user` | 用户级 LaunchAgent：只在有人登录后运行。无 sudo 时才用它 |
| `--listen host:port` | 改监听地址（写进 config 并回读确认） |
| `--upgrade` / `--uninstall` / `--purge` | 升级 / 卸载（保留数据）/ 连数据一起删（需二次确认） |
| `--verify` | **体检当前部署**（不改任何东西）：二进制/配置/服务状态/`/readyz`/**每个媒体根在守护进程上下文里读不读得到**；退出码 0 全过 / 3 在跑但没就绪 / 1 服务不可用（详见第四节） |
| `--dry-run` | 只打印要做的事 |
| `--version` / `--help` | 打印**安装器脚本**版本 / 用法（脚本版本与应用版本是两回事，见 Linux 一节里的说明） |

装到 `~/.local/bin/zizvideo`，数据在 `~/Library/Application Support/zizvideo`，日志在 `~/Library/Logs/`。
**与面板托管互斥**：系统域里已经有 `cn.zizpanel.zizvideo` 时脚本会拒绝独立安装（同一个 7766 端口）。

### 1.1 完全磁盘访问（独立部署的关键一步）

TCC（隐私保护）拦的是"**读**"这个动作。受保护的位置包括：外置卷、`~/Desktop`、`~/Documents`、
`~/Downloads`、照片图库、邮件等 —— 权限位看着正常，`open` 照样被拒。

- 面板托管时：**面板**持有这个授权，zizvideo 作为它的子进程继承 ⇒ 你不用管。
- **独立部署时**：授权必须给 **zizvideo 自己的二进制**，否则那些目录里的视频**不会被扫描到**。

安装器会自动做这件事：

1. 装完服务后，读你 config 里的 `media_allow_roots`；
2. 写一个**一次性 launchd 作业**，让 **launchd 直接执行** `zizvideo check-access <每个媒体根>`
   —— 为什么绕这一下：TCC 把权限归给**发起进程**，安装器是在你的终端里跑的，终端可能已经授权
   （或者根本没有），用它去读测出来的**不是守护进程的权限**，会给出假结论；
3. 读得到 → 报"✓ 守护进程读得到"；读不到 → 打印引导 + 在 Finder 里选中二进制
   + 打开「系统设置 → 隐私与安全性 → 完全磁盘访问」，然后等你授权后复验（默认最多 60 秒）。

手动授权（安装器已经把你带到这一步了）：

1. 打开 系统设置 → 隐私与安全性 → 完全磁盘访问；
2. 点 `+`，按 `⌘⇧G` 粘 `~/.local/bin/zizvideo`（或直接用安装器打开的那个 Finder 窗口把它拖进去）；
3. 打开右边的开关；
4. 不用重装 —— 跑一次「扫描媒体库」或重启服务即可。**升级不会丢这个授权**（二进制是签名的）。

> 无人值守/自动化：`ZV_ACCESS_PROBE_WAIT=0 bash install-zizvideo.sh` 只报告不等待，退出码仍为 0。
> 事后再验一次：`~/.local/bin/zizvideo check-access /你的/媒体根`（输出一行 JSON，`readable` 就是答案）。
> 想看"到底有没有全盘权限"：`zizvideo check-access --fda`（**启发式**，别当判决 —— 见下）。

**为什么 `--fda` 只能是启发式**：2026-10-11 实测，本机 `~/Library/Application Support/com.apple.TCC/`
干脆不存在，而系统级 `TCC.db` 在没有 FDA 的普通进程里也可能读得到 ⇒ 用"哨兵文件读得到"下判决会
**假阳性**（比不探测更糟：会让人以为万事大吉、跳过引导）。所以它的文案写的是"**通常说明**已授予"，
真正可信的判据永远是：**去读你实际关心的那个媒体根**。

## 二、发版前自检（做发布的人看）

```bash
make preflight            # **发布前一条命令**：门禁/冒烟/飞牛包/真 Linux/发布目录/镜像漂移 全跑并给结论
make release-check        # = tools/check-release-dir.sh：把"索引 ↔ 产物"对平（含 fnos.json ↔ .fpk）
make publish              # 现在会**先**跑 release-check，不一致就不发
make preflight-post       # **发布后复核**：线上产物下载回来复算 sha256、latest、漏传
```

完整清单（哪些已自动验证、哪些必须真机）见 [`验收清单.md`](验收清单.md)。

它逐条核对：`manifest.json` / `linux.json` / `android.json` 里写的 **sha256 与 size 跟磁盘文件是否一致**、
版本目录的 `version` 与顶层索引的 `latest` 是否等于 `Makefile` 的 `VERSION`、darwin 二进制
`--version` 与**签名身份**、linux 两个架构**是不是静态 ELF**、APK 的 sha256/size/版本号与 `android.json` 是否一致。
门禁里还塞了两个反例（故意改坏 sha、故意改坏 latest）证明它**真的会红**，不是摆设。
查历史版本可以 `bash tools/check-release-dir.sh --version 0.6.4-mvp`。

## 三、Linux（systemd）

zizvideo 是纯 Go + 内嵌前端 + SQLite，交叉编译 `CGO_ENABLED=0` 的静态二进制在 Linux 上直接可跑
（`make check` 里就有 linux/amd64 + linux/arm64 的交叉编译门禁）。Linux 侧用 `install-zizvideo-linux.sh`：

```bash
sudo bash install-zizvideo-linux.sh --listen 0.0.0.0:7766
```

它做六件事：按架构从**平台专属清单** `linux.json` 挑包 → 下载并**逐字节校验 sha256**（不符就拒）
→ 放二进制到 `/opt/zizvideo/zizvideo` → 建专用系统用户 `zizvideo` 并写 `/etc/zizvideo/config.json`
（已存在则不动）→ 装 `zizvideo.service`（systemd：开机自启、`Restart=always`、
`NoNewPrivileges/ProtectSystem=full/ProtectHome=read-only` 只放开数据目录）→ 起服务并用 `/readyz` 验收
（**验收不过就是失败**：首次安装如实报错；升级则回滚到旧二进制，绝不谎报"安装完成"）。

`--upgrade` 只换二进制；`--uninstall` 停服务（数据保留）；`--purge --yes` 连数据目录一起删并回读确认；
`--dry-run` 只走流程不落盘。Linux 没有 TCC，**不需要**完全磁盘访问那一步；外置盘只需要挂载点服务用户可读。

**两个安装器的 `--version` 含义不同（容易踩）**：macOS 那边 `install-zizvideo.sh --version` 打印的是
**安装器脚本**版本（`1.1.2` 这种）；Linux 这边 `install-zizvideo-linux.sh --version <版本>` 是**断言镜像 latest
就是该版本**（对不上直接拒绝 —— 防"版本已翻页还去装旧包"，**不是**"装某个旧版本"），要打印脚本版本用
`--script-version`（当前 `1.0.0`）。两个脚本各自独立演进，脚本版本号并不相等，**别拿它当应用版本**：
应用版本看镜像索引的 `latest`。

**验证状态（2026-10-11，别照旧印象）**：
- ✅ **发布的 Linux 二进制**已经在**真 Linux（容器）**上跑通全链路（arm64 原生 + amd64 模拟：起服务、SQLite 迁移、
  建库/扫描/首页/`Range` 流式）—— 复现：`make linux-verify API=1`；离线容器镜像 `make docker-tar` 也已验（`docker load` 回来能跑）。
- ✅ 安装器本身的逻辑（挑包/sha256 校验/拒过期版本/起不来就回滚/单元文件/配置生成）在**沙箱门禁**里全覆盖
  （假 systemctl/useradd、`file://` 当镜像、不碰真系统）—— 复现：`make check`。
- ❌ **没在真 init 系统上跑过安装器**（本机没有 systemd、容器里也没有 init）⇒ `systemctl enable --now` 的真实行为、
  开机自启、`journalctl` 落盘这几处要在 NAS/服务器上确认（步骤见 [`验收清单.md`](验收清单.md)）。

**为什么 Linux 走单独的 `linux.json` 而不是 `manifest.json`**：后者是**面板的契约**（只认 darwin、
按 `arch` 选包），同一份里塞 darwin/arm64 与 linux/arm64 会让面板给 macOS 装到 Linux 二进制。
`make release` 现在同时产出 `linux/amd64` + `linux/arm64`（`CGO_ENABLED=0` 静态、不签名），
`make-app-index.py` 把它们写进 `linux.json`（有 linux 产物才写），`make publish` 会把
`linux.json` 与 `install-zizvideo-linux.sh` 传到 app 级稳定路径并复验线上可达。

## 四、装完自查（推荐做一次）

**单文件版**（装完就能跑，不必另下脚本；**不改任何东西**）：

```bash
sudo bash install-zizvideo.sh --verify            # 系统级部署（默认）
bash install-zizvideo.sh --user --verify          # 当初用 --user 装的，体检时也要带 --user
```

它检查：二进制能不能跑（`--version`）、配置能不能解析、数据目录在不在、launchd 里的状态、
`/readyz` 通不通、以及**每个媒体根在守护进程上下文里读不读得到**（复用安装时那套一次性 launchd 作业，
结论可信；拿不到 sudo 会如实说"无法在守护进程上下文里探，这不等于读不到"，不猜）。
退出码 0=全过、1=有 ✗。

**两者覆盖面一致**（2026-10-11 起：数据库是否在数据目录内、磁盘余量、签名身份、媒体根不存在时提示"挂盘了吗"，
安装器单文件版也会报）。区别只是：安装器是**单文件快速版**（装完就能跑），`tools/verify-deploy.sh` 明细更多
（Linux 静态性、`--as-daemon` 守护进程上下文复探、容器识别等）。

**功能更全的自查脚本**（在仓库里）：

```bash
bash tools/verify-deploy.sh                       # 自动找默认路径（macOS/Linux 都支持）
bash tools/verify-deploy.sh --config /etc/zizvideo/config.json --bin /opt/zizvideo/zizvideo
```

**退出码怎么读**（两个脚本一致，`--help` 里也写了）：`0` = 关键项全过、`3` = **服务在跑但没就绪**
（媒体根/磁盘/ffmpeg 的问题，按提示修，**别重启服务**）、`1` = 服务不可用（没起来/端口不对，查日志）、
`2` = 参数或环境问题。也就是：**503 是"能修"，无响应才是"坏了"**。

它真跑一遍并逐条如实报告：二进制版本与**是否静态**（Linux 上动态链接的包在极简 NAS 会因缺 ld.so 起不来）、
配置能否解析、`data_dir` 是否可写、**数据库是否在数据目录内**（不在的话备份/卸载会漏掉它 ——
zizvideo 启动时也会警告这一条）、`media_allow_roots` 是否为空、服务在 launchd/systemd 里的状态、
`/readyz` 的每一项（db/ffmpeg/ffprobe/磁盘/媒体根）、以及**每个媒体根到底读不读得到**。
macOS 上它会明确提醒："当前身份的探测结果 ≠ 守护进程的身份"，并额外给一次完全磁盘访问的启发式探测。

## 五、升级与回滚

- 升级：重跑安装器（或 `--upgrade`）。它会保留 config、数据、以及 TCC 授权。
- 失败的升级会**回滚**：二进制与 plist 恢复成改动前，并把恢复出来的服务重新 bootstrap
  （老实现的失败升级会把用户丢在"服务停着"，脚本里现在有一条门禁盯着这个）。
- 回滚不干净时脚本会**如实说**（不会打印"没有留下半截"）。

## 六、故障排查速查

| 现象 | 先看这里 | 常见原因 |
|---|---|---|
| 桌面/网页打不开 | `curl -s http://127.0.0.1:7766/readyz \| python3 -m json.tool` | 服务没起（`launchctl print system/com.zizvideo.server` / `systemctl status zizvideo`）、端口只绑了 127.0.0.1、端口被面板托管的那份占了 |
| 服务"起来了"但网页显示未就绪（`/readyz` 503） | 看 `/readyz` 里**哪一项没过**：`curl -s -o - -w '\n%{http_code}\n' http://127.0.0.1:7766/readyz`；或直接跑 `--verify` | 503 ≠ 服务坏了：**媒体根不存在/读不到**（没挂盘、目录名写错、权限不够）最常见；其次是缺 ffmpeg、数据目录不可写 |
| 库里没有视频 / 扫描扫不到 | `bash tools/verify-deploy.sh`，再看 `zizvideo check-access <媒体根>` | **macOS 上多半是完全磁盘访问没给**（受保护目录：外置卷、桌面、文稿、照片库…）；也可能是媒体根不在 `media_allow_roots` 里 |
| 不确定"到底谁读不到" | `sudo bash tools/verify-deploy.sh --as-daemon` | 在**守护进程自己的上下文**里复探（macOS 一次性 launchd 作业；Linux 用服务用户）。默认那次只代表**你当前的身份**，不代表守护进程 |
| 装完就退 / 反复重启 | macOS：`log show --predicate 'process == "zizvideo"' --last 5m`；Linux：`journalctl -u zizvideo -n 50` | 配置读不了、端口占用、数据目录不可写、数据库损坏 |
| 升级后数据不对 | 看数据目录里的 `zizvideo.db.pre-upgrade.*`（飞牛）或升级前的备份 | 飞牛升级会**先停服务再备份库**、只留最近 2 份；要回滚就是停服务、用它覆盖 `zizvideo.db`、再起服务 |
| 网页能看但删不掉文件 | 删除是"删文件要口令 + 路径在允许根内 + 删后回读" | 路径不在允许根里、或文件删不掉（那时**记录也不会被删**，这是设计） |
| 磁盘满/空间异常 | `df -h <data_dir>`；飞牛看 `zizvideo.db.pre-upgrade.*` | 收件箱堆积、转码缓存、升级备份（只留 2 份） |
| 手机 App 连不上 | App 里填的地址要能被手机访问到 | 绑了 127.0.0.1、防火墙、不在同一网段 |

**为什么 503 值得单独记一条**：容器编排器（compose healthcheck / k8s probe）会把 503 当"没就绪"，
所以"没挂媒体卷的容器被判 unhealthy、反复重启"这句话的根因可能就是这个 —— 容器入口因此**只把真实存在的
媒体根写进配置**，并把缺失的明确报出来；飞牛的应用日志也会把 503 逐项翻译（"媒体根不存在或读不到：
在应用设置里授权，或放进共享目录 zizvideo/media"），而不是只说"还没就绪"。

一句话原则：**先 `verify-deploy.sh` 拿到事实，再动手改**；凡是"要权限/要删除"的动作，脚本都会先讲清楚它要动什么。

## 七、安装器与自查脚本自身怎么被验证

`tools/test-installer.sh`（`make check` 的一部分，**全程沙箱**：假 launchctl / 假 sudo / 假 open / /tmp 路径）
覆盖（**条数见 `make check` 输出**：会随门禁增长）：`--purge` 删除前守门、config 写入回读、回滚重新 bootstrap、证书指纹硬编码、
交叉编译（linux/amd64 + arm64）、完全磁盘访问的四种路径（读得到 / 读不到要引导 /
`ZV_ACCESS_PROBE_WAIT=0` 不等待 / 探测 plist 不残留）、Linux 安装器（sha256 不符必须拒、dry-run、
真装时 daemon-reload、起不来必须回滚不谎报、单元内容、配置 JSON）、飞牛包（必需文件/键、manifest 键值格式、
`platform != all`、`run-as=package`、JSON 合法、`status` 返回 3、未知参数非 0、不硬编码 `/var/apps`、
图标尺寸、没有 fnpack 时不伪造、wizard JSON 形状、config_callback 幂等与如实失败）、
部署自查脚本（配置缺失如实报 ✗、真实例打通健康端点与媒体根、解析 readyz.status）、
发版前自检（sha256/latest 对不平时必须指名道姓地报出来）、、以及**发行目录里的 Linux 二进制必须是静态 ELF 且架构正确**。
全程沙箱（假 launchctl / 假 sudo / 假 open / `file://` 当镜像 / /tmp 路径），并断言**一次都没碰真 sudo**。

## 八、容器（NAS / 自托管通用）

不依赖任何安装器、也不需要苹果签名或 TCC —— 只要机器上有 Docker（群晖/Unraid/飞牛的 Docker、任何 Linux 都行）。
**两条路，按"能不能拉到底座镜像"选**：

| 你的情况 | 走哪条 | 镜像 |
|---|---|---|
| NAS 没有外网 / 拉不到 Docker Hub | **`make docker-tar` → `docker load`**（推荐：这正是我们**验证过并发布**的那一种） | `FROM scratch`（静态二进制不需要底座），配置**构建时烘焙** |
| 能拉到底座镜像，想要环境变量配置 | `make docker-image`（或自己 `docker build docker/`） | `alpine` + `python3` 入口脚本，按 `ZV_LISTEN`/`ZV_DATA_DIR`/`ZV_MEDIA_ROOTS` 生成配置 |

**离线 tar（推荐给 NAS）**：

```bash
make release && make docker-tar DOCKER_ARCH=amd64   # 产物 + docker.json 索引（打完自动刷新）
# 用户侧：
curl -fsSLO https://mirror.zizdog.com:8888/apps/zizvideo/docker/zizvideo-<版本>-amd64.tar.gz
docker load -i zizvideo-<版本>-amd64.tar.gz
docker run -d --name zizvideo -p 7766:7766 -v /你的/data:/data -v /你的/视频:/media:ro zizvideo:<版本>-amd64
```

默认配置烘焙在里面（`0.0.0.0:7766` / 数据 `/data` / 媒体 `/media`）；要改就挂一份自己的进去：
`docker run -v /你的/config.json:/config.json … <镜像> --config /config.json`。索引 `docker.json` 与
`fnos.json` 同思路（app 级稳定路径、`file`/`sha256`/`size`/`arch`），`make publish` 会传包+索引并复验线上可达，
`make preflight-post` 会把 tar 下载回来复算 sha256。

**alpine 版（需要能拉底座）**：镜像里**不在镜像内编译**（用发行版里的静态二进制），基础镜像 `alpine` + `python3`
（入口脚本要它生成/合并配置）。`docker/entrypoint.sh` 首次启动按环境变量写 `config.json`（`ZV_LISTEN` /
`ZV_DATA_DIR` / `ZV_MEDIA_ROOTS`，冒号分隔），**已有配置绝不覆盖**；数据在 `/data` 卷里，容器以**非 root**
用户运行，所以宿主挂载目录的属主要与容器内 uid 对得上（`docker run --user $(id -u):$(id -g)` 也行）。

```bash
make release
make docker-image DOCKER_ARCH=amd64     # = cp 二进制进 docker/ + docker build（没有 daemon 会如实失败）
docker run -d --name zizvideo -p 7766:7766 \
  -v /你的/data:/data -v /你的/视频:/media:ro -e ZV_MEDIA_ROOTS=/media zizvideo:local
```

**验证状态（2026-10-11 实测，别照旧文档以为"没验过"）**：
- ✅ 本机 docker daemon 可用（29.5.2 linux/aarch64）⇒ **真的构建过镜像、真的跑过容器**：
  `linux/arm64` 原生 + `linux/amd64`（qemu 模拟）都起得来、SQLite 迁移成功、
  API 全链路（建管理员/登录/建库/扫描/首页/`Range` 流式 206）通过 —— `make linux-verify API=1`。
- ✅ `make docker-tar` 导出的 tar **真的 `docker load` 回来跑起来**（`/readyz` 有响应、日志版本正确）；
  scratch 里没有 ffmpeg，所以 `/readyz` 是 503（**"服务在跑但没就绪"**，不是没起来）。
- ❌ **alpine 版没验过**：本机拉不到 Docker Hub（`alpine:3.20` 超时）⇒ 这一版的 Dockerfile 只做了结构门禁
  （非 root/VOLUME/EXPOSE/入口脚本语法），**没有真正 build 过**。要发它，请在能拉底座的机器上 `make docker-image` 验一次。

## 九、飞牛（fnOS）应用

zizvideo 在飞牛上是**独立端口服务**型的 `.fpk` 应用（对应官方文档里的 B 类：应用自带 HTTP 服务、
不需要复用 NAS 登录态）。包源在仓库 `fnos/zizvideo/`：

```
fnos/zizvideo/
├── manifest                  # key=value（**不是 JSON**）：appname/version/platform=x86/service_port=7799…
├── ICON.PNG / ICON_256.PNG   # 64×64 与 256×256（官方硬要求）
├── config/privilege          # run-as=package（最小权限，**不用 root**）
├── config/resource           # data-share: zizvideo/media（应用自己的共享目录）
├── app/ui/config             # 桌面入口 zizvideo.main + 管理员入口（readonly）
├── wizard/install|config|uninstall
│                             # 安装向导（额外媒体根）、应用设置里的配置表单、卸载时的"是否删数据"
│                             #   字段类型只能用 text / password / switch（fnpack 实测）
├── app/bin/zizvideo          # 打包时放进去的 Linux 静态二进制（x86 用 amd64，arm 用 arm64）
└── cmd/main                  # 生命周期：start / stop / status（没跑必须返回 3，未知参数 1）
```

打包与安装：

```bash
make release            # 会同时出 darwin 与 linux/amd64 + linux/arm64 产物
make fpk                # = tools/make-fnos-pkg.sh：准备待打包目录 + 调官方 fnpack 出 .fpk
make fpk FPK_ARCH=arm64 # 给 arm 设备打（manifest 的 platform 会自动改成 arm）
# 产物：dist/apps/zizvideo/fnos/zizvideo-<版本>-x86.fpk（app 级稳定路径）
# 真机安装：appcenter-cli install-fpk dist/apps/zizvideo/fnos/zizvideo-*.fpk
```

**从镜像安装**（发布后飞牛用户的最短路径）：

```bash
# 在飞牛设备上（或先下到本机再拷过去）
curl -fsSLO https://mirror.zizdog.com:8888/apps/zizvideo/fnos/zizvideo-<版本>-x86.fpk
appcenter-cli install-fpk zizvideo-<版本>-x86.fpk
# 索引（机器可读）：https://mirror.zizdog.com:8888/apps/zizvideo/fnos.json
```

`.fpk` 放在 **app 级稳定路径** `apps/zizvideo/fnos/`（版本目录会被 `make publish` 按规矩 prune 掉，
包跟着走就 404 了 —— 与 APK 放 `android/` 同一思路），并有一个 `fnos.json` 索引（`platform: fnos`、
`version` 是包版本、`server_version` 是它搭载的服务端版本、每个架构一条 `file`/`sha256`/`size`）。
`make fpk` 打完包会**立刻刷新索引**（否则索引里还是上一份包的 sha256，而 `make release-check` 会正确地报
"fnos.json 与 .fpk 不一致"）；`make publish` 会传包与索引，并在复验阶段核对线上可达、大小一致。

打包后的自检：

```bash
bash tools/check-fnos-fpk.sh            # = make fpk-check：解开 .fpk 逐项核对
```

它查的是"`fnpack build` 成功"**查不到**的东西：manifest 版本与产物是否同源、`platform` 与内嵌二进制
架构是否一致、二进制是不是**静态 ELF**、8 个生命周期钩子是否都在、`desktop_applaunchname` 是否真在
入口配置里、入口引用的 `images/icon_{0}.png` 两个尺寸是否都在包里且尺寸对、**入口端口与 `service_port` 是否一致**（fnpack **实测不替换** `{port}` 占位符，所以端口
只能硬写并与 manifest 对齐，靠门禁盯住）、图标尺寸、`run-as=package`。当前产物 **22 项全过**。

**官方打包器 fnpack 有 macOS 版**（Apple Silicon / Intel 都有，见
[官方文档](https://developer.fnnas.com/docs/cli/fnpack/)）。放进 `./.tools/fnpack`（gitignored）后
`make fpk` 会优先用它，脚本在 PATH 里找也行。**本仓库已经在 macOS 上真打出过 .fpk**
（`zizvideo-0.6.5-x86.fpk`，约 5.68 MB，`fnpack` 自己的校验通过，包内含 `cmd/main` 与 `app/bin/zizvideo`）；
门禁里也内置了这条真打包（有 fnpack 就跑、没有就如实跳过）。

**向导字段类型只认 `text` / `password` / `switch`** —— 这是 `fnpack 1.2.3` **实测**出来的：
官方那份开发 Skill 文档里还列了 `radio`/`checkbox`/`select`/`tips`，但用它们打包会被
`File install is not valid ... content validation failure` 直接拒掉（我照文档写完就被拒了，
改成 `text`/`switch` 才过）。**以真打包器为准**，门禁也按这三个类型卡。

**装完在设备上自检（只读，随包安装）**：

```bash
sh /var/apps/zizvideo/cmd/verify              # 自动找应用目录与端口
sh /var/apps/zizvideo/cmd/verify /vol1/视频    # 顺便验一个你想加的媒体根
```

它**不改任何东西**（不建文件、不重启服务），逐条报：应用目录 / 二进制 `--version` / 配置与数据目录可写 /
`cmd/main status`（服务在不在跑）/ `/readyz` 每项 / **每个媒体根应用用户读不读得到**（用
`zizvideo check-access` 自己探，不是拿你的身份猜）。退出码与另外两个体检脚本**一致**：
`0` 全过、`3` **服务在跑但没就绪**（503 是"能修"，别重启）、`1` 有实打实的 ✗、`2` 环境不对。
设备上若连 `curl`/`wget` 都没有，它会**如实说"测不了健康端点"**，而不是假装通过。
`tools/check-fnos-project.py` 会在交付前把它的三种退出码都跑一遍（改坏判据会红）。

**没有 `fnpack` 时脚本会如实报错**，不会伪造一个"看起来像 .fpk"的压缩包（假包会让用户装不上
还以为是我们的问题）；`--stage-only`（或 `make fpk STAGE_ONLY=1`）只准备目录。

在应用设置里改**媒体根**：fnOS 会走 `wizard/config` 收集值并调 `cmd/main config_callback` —— 它会
**幂等**地把值合并进 `config.json`（原有媒体根不丢）、然后重启服务；写配置失败就保持原配置并如实报错。
**端口不在这个表单里**：端口只由 `manifest` 的 `service_port` 与桌面入口的 `port` 声明一次
（用户改端口会让桌面入口指错地方 —— 两份真源必然漂移，所以干脆不给改）。

`status` 的判据是"pidfile 里的进程**确实是我们的二进制**"（`kill -0` 之后再核对一次命令行）——
PID 会被系统复用，只看"这个 pid 活着"会把别人的进程当成自己在跑（官方排错清单点名过这条）。

**卸载**：默认**保留**数据（数据库/封面/收件箱）。只有用户在卸载向导里**显式勾选**「同时删除应用数据」
才会删，而且删之前先证明"这确实是本应用的数据目录"（拒绝 `/`、`$HOME`、`/tmp`、`/var/lib` 或任何
不像 `…/zizvideo`、`…/@appdata/…` 的路径），删之后**回读确认**、删不干净就如实非零退出。
没勾选时只打印"已保留"—— 绝不擅自删用户数据。

数据与权限：数据放在应用私有目录（`TRIM_PKGVAR`，卸载默认保留）。**视频有三种放法**：

1. 放进应用的共享目录 `zizvideo/media`（`config/resource` 里的 `data-share`，系统会给应用运行用户授权）；
2. **在飞牛的「应用设置 → 授权目录」里把既有共享目录授权给本应用** —— 我们**不设**
   `disable_authorization_path`，所以这个入口对用户可见。系统会把授权目录以
   `TRIM_DATA_ACCESSIBLE_PATHS`（`:` 分隔）交给应用，`cmd/main` 在 **start 与 config_callback 时
   幂等地合并进 `media_allow_roots`**：原有条目一个不丢、去重、忽略非绝对路径；没有变化就不写盘。
   同理 `TRIM_DATA_SHARE_PATHS`（声明的 data-share）也会一并合进来；
3. 安装向导/应用设置里手填一个应用用户读得到的绝对路径。

（⚠️ 第 2 条依赖飞牛注入的两个环境变量，本仓库开发机没有飞牛设备 ⇒ **未在真机验证**；
合并逻辑本身有沙箱门禁，覆盖了"原有条目保留 / 去重 / 忽略非法项 / 重复 start 幂等"。）

Linux/飞牛没有 macOS 的 TCC，所以**不需要**"完全磁盘访问"那一步。

**已验证 / 未验证**（如实分开写）：
- ✅ **`fnpack build` 真跑过**（macOS Apple Silicon 版官方打包器）：产物约 5.68 MB，
  包内结构经 `tar tzf` 核对（`cmd/*`、`config/*`、`manifest`、图标，以及嵌套 `app.tgz` 里的
  `bin/zizvideo` 与 `ui/*`）；门禁里内置了这条真打包。
- ✅ 包结构/字段/生命周期退出码/最小权限/图标尺寸/向导字段类型都由门禁与 `fnpack` 双验；
  打好的包再由 `tools/check-fnos-fpk.sh` 解开逐项核对（22 项全过）。
- ✅ 生命周期钩子 `install_callback`（建目录+写配置+并入授权目录，幂等）与 `upgrade_callback`
  （**不覆盖正常配置**；配置损坏时备份成 `config.json.broken.<时间戳>` 再重建）都有沙箱门禁。
- ✅ **升级安全网**（官方要求"升级前备份或验证可回滚数据"）：`upgrade_init` 先**停服务**（数据库静止，
  备份才可信）；`upgrade_callback` 把数据库备份成 `zizvideo.db.pre-upgrade.<旧版本>` ——
  同版本不重复备、只保留最近 2 份（老 NAS 卷小）、**不是 SQLite 的文件不备**（不把不确定的东西当库）、
  备份失败如实说但不算升级失败。四条行为都有沙箱门禁。
- ❌ **真机 `appcenter-cli install-fpk` 没跑过**（本机没有飞牛设备）：向导交互、桌面入口、
  授权目录（`TRIM_DATA_ACCESSIBLE_PATHS`）这几处只能在设备上确认。
