# 短视频 / 短剧分离设计（2026-10-10 用户拍板）

> 用户原话："将短视频和短剧独立开，共显示、管理逻辑独立开。"
> 三个决策点（用户已选）：
> ① **拆到 B 层**：内容形态互斥 + 后台两块 **+ 媒体库也分类型**；
> ② **归属由目录结构决定**：库声明为「短剧库」⇒ 里面的目录/文件按目录结构归剧集；
> ③ **首页硬排除剧集**，删掉 `feed_hide_series` 开关。
>
> 目标：**显示面共用一套**（feed/卡片/播放页/TV 全屏都不分家），**管理层各写各的**
> （短视频管理 / 短剧管理），为后续「其它平台 + 独立部署」打底。

## 1. 概念定稿

| | 短视频（short） | 短剧（drama） |
|---|---|---|
| 载体 | **短视频库**（`library.kind='short'`） | **短剧库**（`library.kind='drama'`） |
| 一条视频是什么 | 散片（独立内容） | 某一部剧的一集 |
| 归组依据 | 无（就是自己） | **目录结构**：库下的一级目录 = 一部剧（`series.dir_path`） |
| 出现在首页 feed | ✅ 只有它 | ❌ 永不出现（硬规则） |
| 出现在「剧场」 | ❌ | ✅ 只有它 |
| 后台板块 | 短视频管理 | 短剧管理 |

- **一条 media 的形态由它所在的库决定**（`media.library_id → media_libraries.kind`）：
  不新增 `media.kind` 列，避免两份真源不一致；需要的查询都本来就要 JOIN 库。
- 库的类型是**创建时选**的，之后可改（改动会同时改变扫描规则与后台归属；见 §5 风险）。

## 2. 数据模型（migration 0023）

```sql
ALTER TABLE media_libraries ADD COLUMN kind TEXT NOT NULL DEFAULT 'short';  -- short | drama
CREATE INDEX IF NOT EXISTS idx_media_libraries_kind ON media_libraries(kind);
-- 首页/剧场都按 kind 过滤，series 已按 library_id 组织
-- 删掉首页那个开关（结构上不再需要"混着放"）
ALTER TABLE feed_state DROP COLUMN feed_hide_series;   -- 迁移里写成幂等（先查 pragma）
```

- 迁移时**存量库的默认类型**：有 ≥1 个系列的库判 `drama`，其余判 `short`
  （用户现有的「短剧」库已经有 series，自动落到 drama；纯散片库不受影响）。
  这条要在迁移里用一条 `UPDATE` 实现（`WHERE id IN (SELECT DISTINCT library_id FROM series ...)`）。
- 被 `series` 引用过的 media：迁移后若它所在库是 `short`，属于历史脏数据 —— 迁移时把这些库也一并判 `drama`
  （即"有系列的库 = drama"这条规则同时覆盖它们），保证不出现"短剧库外还有剧集"。

## 3. 扫描规则（按库类型分叉）

- `short`：行为**与今天完全一样**（扫目录、探元数据、对账）。
- `drama`：在上面基础上**多一步归剧**：
  1. 库根下的一级子目录 = 一部剧；用 `series.dir_path` 匹配（不存在就建，标题取目录名）；
  2. 目录内的文件 = 该剧的剧集，`series_media` 里按 §4 的顺序写入；
  3. 库根**直接**放着的文件（不在任何子目录里）= 未归组剧集：仍算 drama（不进 feed），
     后台「短剧管理」里用一个"未归组"分组显示，让用户手动拖进某部剧。
- 改名/移动识别的既有语义**不变**（`migrateRenamed` 保 id），只是 drama 库里多维护一层
  `series_media` 归属；目录改名 = 剧改名（按 `dir_path` 匹配），不要新建一部剧。

## 4. 集号与排序

- 集号**沿用现有识别**（`detect.EpisodesFor`：季节/集号），拿不到就按文件名自然序。
- `series_media.position` 是"展示顺序"（后台可拖），`season/episode` 是"文件名识别出的编号"
  （识别不出就是空，**不许猜**——这是既有约定）。

## 5. 接口与前端

- 新增查询参数：`GET /api/v1/media?kind=short|drama`（默认不过滤，管理面用）、
  `GET /api/v1/series` 只返回 drama 库的剧。
- **`/api/v1/feed/next` 硬排除 drama**（SQL JOIN `media_libraries` 过滤 `kind='short'`）；
  删除 `feed_hide_series` 设置项（前后端一起删，`PATCH /feed/settings` 不再接受该字段）。
- 显示面**不动**：feed、卡片、播放页、TV 三栏/全屏、进度/收藏/稍后/历史都共用同一套。
- 剧场页（`#/series`）只列 drama 库的剧；空态文案改成"还没有短剧库"。
- 后台侧栏（这轮已经改成 4 字标题 + 可折叠）拆成两块：
  「短视频管理」= 媒体列表(仅 short) + 去重 + 清理缺失 + 待审；
  「短剧管理」= 剧场/导入/识别/选集/上传归剧 + 剧集缺失。
  两块的**规则各写各的**（例如短视频支持批量随机排序、去重；短剧以剧为单位组织）。

## 6. 实施顺序（每步都能单独跑 `make check` + 独立提交）

1. **数据层**：migration 0023 + `domain.LibraryKind` + storage 读写/校验 + 存量归类 UPDATE + 迁移测试。
2. **扫描层**：drama 库的目录→剧集归组 + 测试（含"目录改名=剧改名""库根散片=未归组"）。
3. **接口层**：`kind` 过滤 + feed 硬排除 + 删 `feed_hide_series`（含前端设置项）+ 测试。
4. **后台**：按新边界拆 `admin.js`（短视频管理 / 短剧管理），同时把 4 字标题与折叠菜单保留。
5. **前端**：剧场空态、上传目标（上传到 drama 库时必须选/新建剧）等收尾。
6. **文档**：CONTRACT.md（库类型与 feed 语义）、坑清单、状态文档。

## 7. 风险与取舍

- **改库类型**会改变内容可见性（short → drama 会从首页消失）：后台改类型时要有明确提示，
  且**不改文件、不改记录 id**（随时可改回）。
- **目录结构决定归属**意味着"把文件随手丢进短剧库根"会变成"未归组剧集"而不是短视频 ——
  这是用户选的语义（②），后台要用一句人话提示，别让用户猜。
- **不做**两套表/两套 API（用户没选 C）：显示与播放继续共用一份实现，避免重复代码。
