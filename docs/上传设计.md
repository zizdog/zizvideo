# 用户上传（UGC）设计基线 —— 2026-09-24 用户拍板

> 用户决定："1-4 都按你的建议" ⇒ ①**白名单**上传权 ②**要审核**（先落私有 inbox）③**要转码**（兼容优先）
> ④配额 = 每人默认 **50 条 / 20GB**，磁盘可用低于 **20GB** 时拒绝新上传并明说。
> 本文件是施工图：先照它做 P0，再 P1（转码）。改动别偏离这几条，要改先讨论。

## 一、目标与边界

**目标**：让"内容从哪来"不再只靠管理员手工 —— 被授权的用户能上传自己的视频，进待审区，
管理员通过后自动进正式库（能识别剧集、生成封面、转码成兼容格式）。

**不做**（P0 明确不做，避免铺太开）：公开注册即上传、评论/弹幕、多码率、断点续传客户端 SDK、上传者收益。

## 二、权限（白名单）

- 新增 `users.can_upload INTEGER NOT NULL DEFAULT 0`（迁移 0014）。
- 管理员在后台「用户」页逐人开关"允许上传"（复用现有用户行操作区）。
- 判定：`can_upload=1 && status=active` 才放行；管理员天然有（`role=admin`）。
- 与媒体库权限的关系：上传落点是**该用户的 inbox**，不需要库授权；审核通过后进正式库时由**管理员**选择目标库（管理员有全部库的权限）。

## 三、数据模型（迁移 0014_uploads.sql）

```sql
ALTER TABLE users  ADD COLUMN can_upload INTEGER NOT NULL DEFAULT 0;
ALTER TABLE media  ADD COLUMN uploader_id TEXT;            -- 谁传的（管理员上传也可填）
ALTER TABLE media  ADD COLUMN review_state TEXT;           -- '' 正常 | 'pending' 待审 | 'rejected' 驳回
ALTER TABLE media  ADD COLUMN review_note  TEXT;           -- 驳回原因（给人看的）
CREATE INDEX IF NOT EXISTS idx_media_review ON media(review_state, uploader_id);

-- 上传会话落库（现在是内存 Map，重启就 404 —— 手机传大文件必然遇到）
CREATE TABLE IF NOT EXISTS upload_sessions (
  id          TEXT PRIMARY KEY,
  user_id     TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name        TEXT NOT NULL,          -- 原始文件名（清洗后）
  size        INTEGER NOT NULL,
  received    INTEGER NOT NULL DEFAULT 0,
  chunk_size  INTEGER NOT NULL,
  dir         TEXT NOT NULL,          -- inbox 落点（绝对路径，必须在允许根内）
  status      TEXT NOT NULL,          -- open | done | failed
  media_id    TEXT,                   -- 完成后指向 media（待审状态）
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);
```

- `media.review_state='pending'` 的行：**只有上传者本人与管理员可见**（scope 之外再加一层：普通用户查询默认排除 pending）。
- 通过 → `review_state=''`（正常）并移入目标库；驳回 → `'rejected'` + `review_note`（记录保留，磁盘文件保留，等用户自己删或管理员清理）。

## 四、落盘

- inbox：`<数据目录>/inbox/<user_id>/<yyyy-mm-dd>/<清洗后的文件名>`。
  - 必须在允许根内（复用 `config.Roots` 判据 + 删后回读的纪律）。
  - 文件名清洗：去路径分隔符/控制字符，长度上限，重名加 `-1/-2` 后缀。
- 审核通过移动（`os.Rename`，同盘不复制字节）到目标库的库根（或该库的 `dir_path` 规则）。
- `--purge` 语义：inbox 属于数据目录，卸载默认保留。

## 五、接口（都走现有信封 + CSRF 双提交）

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/uploads/start` | 开一个上传会话（`{name,size,chunk_size}`）→ `{id, received}`；**落库** |
| `PUT` | `/api/v1/uploads/{id}/chunk?offset=N` | 传一块（幂等：offset 与已收长度不一致就 409 + 当前长度） |
| `POST` | `/api/v1/uploads/{id}/finish` | 收尾：校验大小 → 探测（ffprobe）→ 落 media（`review_state='pending'`, `uploader_id`）→ 抽封面 |
| `GET` | `/api/v1/uploads/{id}` | 续传用：返回已收长度（断线后前端从这里接着传） |
| `GET` | `/api/v1/me/uploads` | 我传的（含 `review_state`/`review_note`） |
| `GET` | `/api/v1/admin/uploads/pending` | 待审列表（管理员） |
| `POST` | `/api/v1/admin/uploads/{mediaId}/approve` | 通过：选目标库（`library_id`）→ 移动 + 清 `review_state` |
| `POST` | `/api/v1/admin/uploads/{mediaId}/reject` | 驳回：`review_note` 必填 |
| `GET`/`PATCH` | `/api/v1/admin/uploads/quota` | 配额（默认 50 条 / 20GB；磁盘阈值 20GB） |

## 六、配额与安全（不做会被玩坏）

- 计数：`SUM(size) WHERE uploader_id=? AND deleted_at IS NULL` + 条数；超限 → 413/403 + 人话原因。
- 磁盘：`statfs(数据目录).free < 20GB` → 拒绝并说明"服务器空间不足"。
- 单文件上限：复用 `upload_max_file_mb`（默认 8192）。
- 内容去重：finish 时算 **sha256**（流式，不占内存），与已有 media 的 hash 比 → 命中则拒绝并指向已有记录
  （避免同一集传十遍）；需要给 `media` 加 `content_hash TEXT`（本迁移一起加）。
- 频率：每用户同时最多 2 个 `open` 会话。

## 七、审核与转码（P1）

- 通过时可选"顺手转码"：进 `job_tasks`，ffmpeg 转 H.264/AAC + 720p，产出替换 `media.path`（原文件保留到转码成功后删）。
- 转码失败：记录 `error_class/message`，media 保持原文件可用（不许"转码失败就没得看"）。
- 剧集：批量上传时按文件名识别集数（复用 `media.ParseEpisode`）→ 建"剧场草稿"（`series` + `series_media`），审核通过即成形。

## 八、前端

- 网页：`#/upload`（普通用户，需 `can_upload`）—— 多选、总进度、单文件进度、可取消、断线续传；
  `#/me/uploads` 我的上传（状态/驳回原因）；后台「待审」页（预览 + 通过(选库)/驳回(填原因) + 批量）。
- 安卓：系统文件选择器（SAF）多选 → 前台服务后台上传（走同一套分片接口，息屏不断）。
- 文案纪律：每条 ≤40 字，细节进折叠项。

## 九、施工顺序（每步都可独立验收）

1. **迁移 0014 + 权限开关**（`can_upload`）+ 后台用户页开关 + 门禁（未授权 403 / 授权可开会话）。
2. **上传会话落库 + 分片/续传**（重启后 `GET /uploads/{id}` 仍能续）+ 断点门禁。
3. **inbox 落盘 + finish（探测/封面/内容 hash 去重）** + 待审可见性门禁（别人看不到 pending）。
4. **待审列表 + 通过(选库移动)/驳回** + 通过后进正式库的门禁。
5. **配额与磁盘阈值** + 门禁。
6. 前端三页（上传/我的上传/待审）+ 安卓 SAF 上传。
7. P1 转码队列。
