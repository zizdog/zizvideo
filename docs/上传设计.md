# 用户上传（UGC）设计基线 —— 2026-09-24 用户拍板

> 用户决定："1-4 都按你的建议" ⇒ ①**白名单**上传权 ②**要审核**（先落私有 inbox）③**要转码**（兼容优先）
> ④配额 = 每人默认 **50 条 / 20GB**，磁盘可用低于 **20GB** 时拒绝新上传并明说。
> 本文件是施工图：先照它做 P0，再 P1（转码）。改动别偏离这几条，要改先讨论。

## 一、目标与边界

**目标**：让"内容从哪来"不再只靠管理员手工 —— 被授权的用户能上传自己的视频，进待审区，
管理员通过后自动进正式库（能识别剧集、生成封面、转码成兼容格式）。

**不做**（P0 明确不做，避免铺太开）：公开注册即上传、评论/弹幕、多码率、断点续传客户端 SDK、上传者收益。

## 二、权限（白名单）

- 新增 `users.can_upload INTEGER NOT NULL DEFAULT 0`（迁移 0014）。
- 管理员在后台「用户」页逐人开关"允许上传"（复用现有用户行操作区）。
- 判定：`can_upload=1 && status=active` 才放行；管理员天然有（`role=admin`）。
- 与媒体库权限的关系：上传落点是**该用户的 inbox**，不需要库授权；审核通过后进正式库时由**管理员**选择目标库（管理员有全部库的权限）。

## 三、数据模型（迁移 0014_uploads.sql）—— 已实现

```sql
ALTER TABLE users ADD COLUMN can_upload INTEGER NOT NULL DEFAULT 0;

-- 一行 = 一次上传（不是 media）：待审内容根本不进 media 表，
-- 所以"别人看不到 pending"是结构性保证，不靠列表过滤兜底。
CREATE TABLE upload_items (
  id             TEXT PRIMARY KEY,
  uploader_id    TEXT NOT NULL,
  name           TEXT NOT NULL,           -- 清洗后的文件名（也就是 inbox 里的名字）
  title          TEXT NOT NULL DEFAULT '',
  path           TEXT NOT NULL,           -- inbox 绝对路径
  size           INTEGER NOT NULL DEFAULT 0,
  received_bytes INTEGER NOT NULL DEFAULT 0,
  content_hash   TEXT NOT NULL DEFAULT '',-- sha256（finish 时算，用于内容去重）
  state          TEXT NOT NULL DEFAULT 'uploading'
                 CHECK (state IN ('uploading','pending','approved','rejected')),
  review_note    TEXT NOT NULL DEFAULT '',
  media_id       TEXT NOT NULL DEFAULT '',-- 通过后的 media.id
  library_id     TEXT NOT NULL DEFAULT '',-- 通过后的目标库
  reviewed_by    TEXT NOT NULL DEFAULT '',
  reviewed_at    TEXT,
  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL
);
```

- 状态机：`uploading → pending → approved / rejected`（只允许沿这条走，重复审核会 409）。
- 断点续传**不需要内存会话**：`upload_items` 一行 + 磁盘上的 `.zvpart` 就是全部状态，
  进程重启后 `GET /api/v1/uploads/{id}` 仍能给出续传位置。
- 通过：文件移进目标库 → 探测+封面 → 写 `media`（`status=ready`）→ 记 `media_id/library_id`。
- 驳回：**先删文件再改状态**（删不掉就不改状态，遵守"删后回读"纪律），`review_note` 留原因。

> 与最初设想的差别（如实记录）：原方案想在 `media` 上加 `uploader_id/review_state/review_note/content_hash`
> 并用列表过滤藏 pending。实测那条路要动 `feed`/`media`/`stats` 三处查询、还要给 inbox 造一个"隐藏媒体库"
> 才能播预览；改成独立的 `upload_items` 表后：普通列表天然看不到待审内容，inbox 也不需要进允许根。

## 四、落盘（已实现）

- inbox：`<数据目录>/inbox/<user_id>/<yyyy-mm-dd>/<清洗后的文件名>`（目录 0700，`.zvpart` 0600）。
  它**不在媒体允许根内**——因为待审内容不在 `media` 表里，也就不需要走库路径校验；
  越界由 `media.Within(path, inboxRoot)` 兜底（路径全部服务端拼，用户输入只进文件名）。
- 文件名清洗：`safeFileName`（去分隔符/控制字符），重名不覆盖：磁盘 + `upload_items.path` 一起避让。
- 审核通过移动：目标必须落在选定库根内（`media.ValidateMediaFile` 复核），
  同卷 `os.Rename`、跨卷复制 + fsync + 删源；进库后 chmod 0644（与扫描到的文件同权限）。
- `--purge` 语义：inbox 属于数据目录，卸载默认保留。

## 五、接口（都走现有信封 + CSRF 双提交）—— 已实现

门禁：`s.RequireUploader`（挂在 `RequireAuth` 内层；管理员天然通过，普通用户要 `can_upload=1 && status=active`），
未授权一律 403 `UPLOAD_NOT_ALLOWED`。

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/uploads` | 开会话（`{name,size}`）→ `{item,quota}`；先查配额、磁盘阈值、扩展名、单文件上限 |
| `PUT` | `/api/v1/uploads/{id}` | 传字节（`Content-Range: bytes a-b/total` 或 `?offset=N`）；offset 与磁盘不符 → 409 + 服务端已有长度 |
| `GET` | `/api/v1/uploads/{id}` | 续传回读：`received_bytes` 以磁盘为准（重启后仍准） |
| `POST` | `/api/v1/uploads/{id}/finish` | 校验大小 → sha256 内容去重 → 定稿为 `pending` |
| `DELETE` | `/api/v1/uploads/{id}` | 取消未定稿的上传（删 `.zvpart` 后回读确认，再删记录） |
| `GET` | `/api/v1/uploads/{id}/stream` | 待审预览（本人或管理员，支持 Range） |
| `GET` | `/api/v1/uploads/{id}/cover` | 待审封面（现场抽帧，复用 media 的封面缓存与单飞锁） |
| `GET` | `/api/v1/me/uploads` | 我传的（全部状态 + 配额） |
| `GET` | `/api/v1/admin/uploads/pending` | 待审列表（带上传者用户名） |
| `POST` | `/api/v1/admin/uploads/{id}/approve` | 通过：`{library_id,title?}` → 移动 + 探测 + 登记 media |
| `POST` | `/api/v1/admin/uploads/{id}/reject` | 驳回：`{note}` 必填 |
| `PATCH` | `/api/v1/users/{id}` | 后台开白名单：`{can_upload:true}`（用户页"允许上传/禁止上传"按钮） |

别人（非本人非管理员）的 `/api/v1/uploads/{id}` 一律 404，不泄露存在性。

## 六、配额与安全（已实现）

- 配额：每人 **50 条 / 20GB**（`uploading + pending + approved` 计数；`uploading` 按声明大小算，防占坑）。
- 磁盘阈值：inbox 所在盘 `free - size < 20GB` 直接拒绝（`UPLOAD_DISK_FLOOR`）。
- 单文件上限：复用 `upload_max_file_mb`（默认 8192）。
- 内容去重：finish 时流式 sha256，同一上传者的 `pending/approved` 命中 → 409 并指向已有条目（顺手清掉重复的 `.zvpart` 与记录）。
- 扩展名白名单与扫描器一致（`ExtAllowed`），落点全部由服务端拼（用户 id + 日期 + 清洗后的文件名）。

## 七、转码队列（P1）—— 已实现（0.1.20-mvp）

**目标**：兼容优先 —— 把 MKV/HEVC/怪异音频/超分辨率的内容转成手机一定能播的 H.264 + AAC + ≤720p。
判据只看编解码与分辨率，**不看浏览器 UA**（服务端不为某个客户端做决定）。

- 入口：① 后台「待审」页的**通过并转码**；② 后台「媒体」页逐行**转码**按钮（可对库里已有内容补转）。
- 排队：`POST /api/v1/admin/transcodes {media_ids}` → `job_tasks`（kind=`transcode`）→ 单工作协程串行跑
  （转码吃满 CPU/GPU，串行才对）；进度看 `GET /api/v1/admin/tasks/{id}` 的 `percent`（当前这一件的百分比）。
- **已兼容不重编**：H.264 + AAC + ≤720p ⇒ 只 `-c copy` 换 MP4 容器并 `+faststart`（几秒钟）；
  视频兼容只有音频不行 ⇒ 只重编音频；其余才重编视频（有 `h264_videotoolbox` 用硬件，否则 `libx264 -preset veryfast -crf 23`）。
- **失败不许毁原件**（红线）：输出写到**同目录**的 `<文件>.zvtranscode`（扩展名不在允许列表里，扫描器会跳过；
  同目录 ⇒ 成功时 `os.Rename` 原子替换、跨卷也不会出现半成品）。转码产物**必须能探测出视频流**才允许替换；
  任何一步失败 ⇒ 删临时文件，`media.transcode_state='failed'` + `transcode_note` 写原因，**原文件一个字节不动、status 仍是 ready**。
- 成功后：`media` 行**就地重探**（`Scanner.RefreshFile`，id 不变 ⇒ 观看进度/收藏/剧场成员关系全都保留）+ 重抽封面，
  `transcode_state='done'`，note 写清"转了还是只换了容器 + 耗时"。
- 界面如实说：媒体页状态列显示 `ready · 已转码 / 转码中 / 转码失败`（失败时鼠标悬停看原因）；
  待审页显示"转码中 1/2 · 当前 45%"→"转码完成：成功 1 / 失败 0"。

**还没做**：剧集草稿（批量上传时按文件名识别集数 → 审核通过即成形：`series` + `series_media`）。
现在的审核通过只入目标库、可选顺手转码；要成剧集仍走后台「剧场」页的导入/识别。

## 八、前端

- 网页：`#/upload`（普通用户，需 `can_upload`）—— 多选、总进度、单文件进度、可取消、断线续传；
  `#/me/uploads` 我的上传（状态/驳回原因）；后台「待审」页（预览 + 通过(选库)/驳回(填原因) + 批量）。
- 安卓：系统文件选择器（SAF）多选 → 前台服务后台上传（走同一套分片接口，息屏不断）。
- 文案纪律：每条 ≤40 字，细节进折叠项。
